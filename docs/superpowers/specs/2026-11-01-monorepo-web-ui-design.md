# Design: bring cairn-web-ui into the cairn repository

Date: 2026-11-01
Status: draft, awaiting approval
Tracking issue: tau-rs/cairn#244

## Plain-language summary

Cairn's engine (this repo) and its web/desktop UI (`tau-rs/cairn-web-ui`) live in
two repositories. The UI depends on the engine in two independent places that
must always name the same engine commit: a vendored copy of the TypeScript
contract that ts-rs generates from the Rust types, and six git-rev pins in the
Tauri desktop crate's `Cargo.toml`. Nothing enforces that they agree. The UI
repo's own tracker records this biting at least four times (#172, #176, #177,
#180) and an open proposal (#181) to add CI machinery just to detect the drift.

This design moves the UI repository into this one, under `apps/web-ui/`, with
its full history. After the move the Tauri crate depends on the engine crates
by path and the web app reads the generated TypeScript bindings straight from
the engine crate's directory. Both drift seams disappear because there is only
one commit. The drift scripts, the commit stamp, and the clone-and-diff CI job
are deleted rather than rewritten.

Analogy: today the UI carries a photocopy of the engine's API and a note saying
which edition it was copied from. The monorepo hands the UI the original.

## Intent and why

- Goal: an engine change that breaks the UI is caught on the PR that makes it,
  not on the next manual re-pin.
- Goal: one place to look for cairn's product surfaces: CLI, daemon, MCP server,
  web/desktop UI.
- Why now: the drift has cost four rounds of manual repair and the next fix
  proposed in the UI repo is more detection machinery. Removing the seam is
  cheaper than policing it.

## Goals, non-goals, anti-goals

Goals
- `apps/web-ui/` contains the former cairn-web-ui repo with history intact.
- The Tauri crate builds against the engine crates by path, not git rev.
- The web app type-checks and builds against the in-tree ts-rs bindings; no
  vendored copy exists.
- CI gates both stacks on every PR, with path filters so Rust-only PRs skip the
  web jobs and web-only PRs skip the engine matrix.
- The old repository is archived with a pointer to the new location.

Non-goals
- Pulling in `tau`, `tau-web-ui`, or any other tau-rs repository.
- Reorganising the UI's internal layout (`web/` and `src-tauri/` stay siblings).
- Folding `graph-viz/` under `apps/` or into a pnpm workspace. It stays where it
  is; a follow-on issue may unify the JS tooling later.
- Changing the engine's crate layout, lints, or CI matrix.

Anti-goals (would make this a failure even if it "works")
- Engine CI becomes slower or needs WebKitGTK/WebView2 system packages for
  jobs that do not touch the UI.
- History of the UI repo is lost or only reachable through the archived repo.
- A new vendoring step replaces the old one. The point is zero copies.

## Constraints

- Engine workspace pins Rust 1.88 via `rust-toolchain.toml`; `rustup` walks up
  directories, so the nested Tauri workspace inherits it. Tauri 2.11 needs
  1.77.2, so this is fine.
- Engine workspace lints `unsafe_code = "forbid"`; the Tauri crate has no
  `unsafe` and will opt into workspace lints only if it joins the workspace.
- Branch protection on `main` requires the single check `ci-summary` and uses
  a merge queue. New web jobs must feed that one summary; no new required
  check names.
- `sync-template.yml` pulls `clippy.toml` and `rustfmt.toml` from `tau`.
  Workflow bodies are not synced, so editing `ci.yml` creates no drift PRs.
- The UI's `web/.prettierignore` excludes `src/contract/`; the bindings keep
  ts-rs' output format and must stay out of prettier's reach wherever they are
  imported from.
- The engine's committed bindings are regenerated by the
  `exports_typescript_bindings` test in `crates/cairn-contract/tests/codegen.rs`.
  Nothing in engine CI today fails if the committed bindings lag the Rust source.

## Decisions made (with the why)

### D1. Target directory is `apps/web-ui/`

Why: cairn already ships three faces (CLI, daemon, MCP). A top-level `web/`
reads as "the UI" and leaves nowhere obvious for a second app. `apps/` makes
the product-list story visible in `ls` for one extra path segment.

Layout after the import:

```
cairn/
├── Cargo.toml              # engine workspace; apps/web-ui/src-tauri excluded
├── crates/                 # engine, unchanged
├── graph-viz/              # unchanged
└── apps/
    └── web-ui/             # = cairn-web-ui repo root, history intact
        ├── web/            # Vite app; imports bindings from the engine crate
        ├── src-tauri/      # own Cargo workspace; cairn-* deps by path
        ├── justfile        # UI verbs, invoked by root CI via `just -f`
        ├── docs/
        ├── audit/
        └── CLAUDE.md
```

### D2. Import by `git subtree add`, not by copying files

Why: subtree keeps every UI commit reachable from this repo's history, so
`git log` and `git blame` under `apps/web-ui/` work. The import is one merge
commit that can be reverted as a unit. Filter-repo style rewriting was
rejected: it gains nothing here and costs a destructive step.

Example:

```
git subtree add --prefix=apps/web-ui https://github.com/tau-rs/cairn-web-ui.git main
```

The `main` ruleset merges by squash only, which would collapse the subtree
merge and every UI commit behind it into one commit. PR 1 therefore lands
with a one-time change of the merge-queue method to merge commit, reverted
to squash immediately after. Decided with the author: history stays
reachable here, so `git blame` on a UI file names the original author and
the SHAs referenced in the UI's handoffs and plans keep resolving.

```
# before queueing PR 1
gh api -X PUT repos/tau-rs/cairn/rulesets/<id> ... merge_method=MERGE
# after PR 1 merges
gh api -X PUT repos/tau-rs/cairn/rulesets/<id> ... merge_method=SQUASH
```

PR 2 and PR 3 squash like any other PR.

### D3. The Tauri crate stays its own Cargo workspace, excluded from the engine's

Why: joining the engine workspace would make `cargo clippy --workspace` and
`cargo nextest run --workspace` compile Tauri on every engine job, which needs
WebKitGTK on Linux and adds minutes to every PR. This violates the anti-goal.
`fuzz/` already uses the exclude pattern. Path dependencies work across
workspaces, so the drift seam is still eliminated.

Before and after for the six engine pins in `apps/web-ui/src-tauri/Cargo.toml`:

| Dependency | Before | After |
|---|---|---|
| cairn-domain | `{ git = "...", rev = "9490ec4" }` | `{ path = "../../../crates/cairn-domain" }` |
| cairn-app | same | `{ path = "../../../crates/cairn-app" }` |
| cairn-infra | same | `{ path = "../../../crates/cairn-infra" }` |
| cairn-contract | same | `{ path = "../../../crates/cairn-contract" }` |
| cairn-service | same | `{ path = "../../../crates/cairn-service" }` |
| cairn-ports | same | `{ path = "../../../crates/cairn-ports" }` |

Root `Cargo.toml` gains `"apps/web-ui/src-tauri"` in `exclude`.

One honest consequence: two `Cargo.lock` files and two `deny.toml` files remain.
Transitive versions may differ between them. The UI's `deny.toml` drops
`unknown-git = "allow"` since no git sources remain.

Folding the Tauri crate into the engine workspace is a possible later step
once engine CI has a cheap way to skip it. It is listed as a follow-on, not
done here.

### D4. The web app imports bindings from the engine crate directory; no copy

Why: this is the whole point. Today `web/src/contract/` holds 33 generated
files (byte-identical to the engine's `crates/cairn-contract/bindings/` at the
pinned rev), plus two hand-authored files: `index.ts` (a barrel) and
`source.ts` (the commit stamp). After the change:

- the 33 generated files and `source.ts` are deleted from `web/src/contract/`;
- `index.ts` stays, hand-authored, and re-exports from the engine bindings;
- the handful of direct imports (`../contract/Revision`,
  `../contract/serde_json/JsonValue`, `../contract/PluginWidget`) resolve to
  the same place.

How the path is resolved (alias versus relative path) is left to the builder;
the recommendation is a single tsconfig `paths` entry plus the matching Vite
`resolve.alias`, so no source file carries a five-segment relative path.

Example of the barrel after the change (one line shown):

```ts
export type { Command } from "@cairn-contract/Command";
```

The `.prettierignore` entry for `src/contract/` is replaced by whatever keeps
prettier away from the engine's bindings directory (they are outside `web/`,
so by default prettier never sees them).

### D5. Engine CI gains a "bindings are current" check

Why: once the UI reads the committed bindings directly, a stale commit of
those bindings becomes the one remaining way to drift. The check runs the
existing codegen test and fails on any resulting diff under
`crates/cairn-contract/bindings/`. This replaces the UI's
`check-contract-drift.sh` with a one-line, clone-free guard.

```
cargo test -p cairn-contract
git diff --exit-code -- crates/cairn-contract/bindings
```

All targets, not only the `codegen` test: the `Collab*` and `Wire*` bindings
are emitted by per-type `#[ts(export)]` tests inside the library.

### D6. One `ci.yml`, path-filtered, one `ci-summary`

Why: branch protection requires exactly `ci-summary`. Adding a second workflow
would need a repo-settings change and a second required check. Instead the
UI's `changes` job (dorny/paths-filter) moves into the engine's `ci.yml`, and
its `web`, `e2e`, and `tauri` jobs join `ci-summary`'s `needs`. The UI's
`contract-drift` job is deleted (D4/D5 make it meaningless).

Path filters, one row per stack:

| Filter | Paths | Jobs gated |
|---|---|---|
| web | `apps/web-ui/web/**`, `apps/web-ui/justfile`, `crates/cairn-contract/bindings/**`, `.github/workflows/ci.yml` | web, e2e |
| tauri | `apps/web-ui/src-tauri/**`, `apps/web-ui/justfile`, `apps/web-ui/deny.toml`, `crates/**`, `Cargo.lock`, `.github/workflows/ci.yml` | tauri |

Engine jobs keep running unconditionally, as today. On `pull_request` the
filter is dorny/paths-filter. On `merge_group` the filter is a plain
`git diff --name-only <merge_group.base_sha> <merge_group.head_sha>` matched
against the same path lists, because paths-filter has no reliable base there
(dorny/paths-filter#280). On `push` to `main` everything runs. Why not force
everything on in the queue, as the UI repo did: that would charge every
Rust-only merge the Tauri build with its WebKitGTK install, which is anti-goal
one. This is my call, not something the author asked for.

The `tauri` job and the `web` jobs call the UI's own justfile via
`just -f apps/web-ui/justfile <verb>` from the repo root, so the UI's "local ==
CI" contract is preserved with no recipe duplication.

### D7. Dependabot: merge the UI's npm and cargo entries; drop Renovate

Why: the engine already uses Dependabot for GitHub Actions; the UI used
Renovate only for action digest pins. In one repo, one bot. The UI's two
Dependabot entries move in with their `directory` rewritten to
`/apps/web-ui/web` and `/apps/web-ui/src-tauri`, groups and labels intact.
`renovate.json` is not imported. The UI's `dependabot-automerge.yml` is
imported as is; the engine has no equivalent and the policy (dev deps, minor or
patch only) is unchanged. The UI's `auto-update-prs.yml` is not imported: the
engine relies on the merge queue with strict protection and has lived without
it.

### D8. Overlapping scheduled workflows: engine's win, UI-specific ones move in

| UI workflow | Engine has | Decision |
|---|---|---|
| `ci.yml` | yes | merged per D6 |
| `claude.yml` | yes | engine's kept; UI's dropped |
| `auto-rerun-flaky.yml` | yes | engine's kept; UI's dropped |
| `coverage.yml` | yes | UI's vitest coverage job merged into engine's as a second job |
| `heavy.yml` | yes | UI's Tauri cross-OS bundle, sign, and SBOM jobs merged into engine's as additional jobs; `v*` tag trigger shared |
| `mutation-weekly.yml` | `mutants-scheduled.yml` | imported under its own name, paths rewritten |
| `nightly.yml` | no | imported, paths rewritten |
| `dependabot-automerge.yml` | no | imported |
| `auto-update-prs.yml` | no | dropped (see D7) |

Why engine wins on overlap: the engine's copies are the ones the template-sync
from `tau` converges toward.

### D9. Local tooling: nested justfile and CLAUDE.md stay; root lefthook learns the UI

Why: `just` and Claude Code both honour nested files when run from a
subdirectory, so UI contributors keep their muscle memory. Git hooks are
repo-wide, so the root `lefthook.yml` gains web `fmt`, `lint`, and `test`
commands with a `glob` on `apps/web-ui/web/**` so Rust-only commits do not pay
for pnpm. The UI's `lefthook.yml` is deleted. The UI's `scripts/claim-plan.sh`
and its CLAUDE.md rule are kept under `apps/web-ui/` unchanged; the engine's
prior-art skill covers the same need from the root.

The UI's `README.md` becomes `apps/web-ui/README.md` with the badge and clone
instructions rewritten. The engine `README.md` gains one paragraph pointing at
`apps/web-ui/`.

### D10. Issue and PR migration, then archive

Why: the ledger lives on GitHub and must stay exhaustive. Open items in the UI
repo at time of writing:

| Item | Decision |
|---|---|
| #180 re-pin both seams to 604d728 | closed by this work; closing comment points at the monorepo PR |
| #181 CI cannot see the seams drifting | closed by this work; closing comment records that the seams no longer exist |
| PR #173 docs roadmap reconcile | merge or close in the UI repo before the import freeze |
| PR #174 ci auto-update classification | close; `auto-update-prs.yml` is not imported (D7) |
| 12 Dependabot PRs | close; they regenerate against the new paths |

After the final stage merges, the UI repo is archived and its README replaced
with a pointer. The repo description is updated to say "moved to
tau-rs/cairn/apps/web-ui".

### D11. One release train

Both repos' `heavy.yml` publish a GitHub Release on a `v*` tag: the engine
with CLI and daemon tarballs plus a CycloneDX SBOM, the UI with Tauri desktop
bundles plus its own SBOM, as a draft. After the merge one tag produces one
release holding all of them. Why: the desktop app links the engine in-process
at the same commit, so a desktop build and an engine build from one tag are
the same artefact set by construction. Two trains would exist only to let
them diverge.

Rules that follow:
- the tag version must equal `version` in `apps/web-ui/src-tauri/tauri.conf.json`;
  the `heavy.yml` release job checks this and fails the run otherwise;
- bumping the desktop version happens in the same PR as any engine version
  bump;
- one `release` job in `heavy.yml` uploads every asset; the UI's separate
  draft-release job is not imported.

Releases page after the first tag:

```
v0.2.0
  cairn-linux-x86_64.tar.gz
  cairn-macos-aarch64.tar.gz
  cairn-desktop-macos-aarch64.dmg
  cairn-desktop-linux-x86_64.AppImage
  sbom-cargo.cdx.json
  sbom-pnpm.cdx.json
```

The Tauri updater signing secrets exist in neither repo today, so signing
stays inert until someone adds them; that is unchanged by this design.

## Staging

Three PRs, each green and revertable on its own. Why staged: the import commit
is large and mechanical; keeping it free of behavioural edits makes review
possible and makes a rollback a single revert.

```
PR 1  import + path deps + CI merge
      ├── git subtree add → apps/web-ui/
      ├── src-tauri/Cargo.toml: git revs → path deps; Cargo.lock regenerated
      ├── root Cargo.toml: exclude apps/web-ui/src-tauri
      ├── ci.yml: changes/web/e2e/tauri jobs + ci-summary needs (D6)
      ├── dependabot.yml merge (D7)
      └── UI still builds from its vendored contract (unchanged)

PR 2  in-tree bindings
      ├── delete web/src/contract/*.ts except index.ts; delete source.ts
      ├── alias + barrel rewrite (D4)
      ├── delete scripts/sync-contract.sh, check-contract-drift.sh, contract-drift job
      ├── engine ci.yml: bindings-current check (D5)
      └── web path filter gains crates/cairn-contract/bindings/**

PR 3  tooling and ledger
      ├── workflow overlap resolution (D8)
      ├── root lefthook.yml + README edits (D9)
      ├── issue/PR migration comments, archive old repo (D10)
      └── ADR docs/decisions/0015-monorepo-web-ui.md recording D1–D11
```

Each PR body carries `Closes #<issue>` for its stage issue; an umbrella issue
links the three.

## What is left to the builder

- Exact alias name and mechanism for D4 (tsconfig `paths` plus Vite alias is
  the recommendation, not a requirement).
- Whether `just -f` or a thin wrapper recipe in the root justfile invokes the
  UI verbs from CI.
- Order of operations inside PR 1 (subtree first, then edits, or edits as a
  second commit on the same branch).
- Cache keys for `Swatinem/rust-cache` in the tauri job (`workspaces:
  apps/web-ui/src-tauri`).
- Whether the UI's `audit/` directory stays as is or gets a one-line README
  pointer; content is not edited.

## Follow-ons (filed as issues, not done here)

- Fold `apps/web-ui/src-tauri` into the engine workspace once engine CI can
  skip it cheaply (D3).
- Unify `graph-viz/` and `apps/web-ui/web/` JS tooling under a pnpm workspace.
- Re-evaluate whether the engine's `coverage.yml` should upload both stacks
  under codecov flags.
